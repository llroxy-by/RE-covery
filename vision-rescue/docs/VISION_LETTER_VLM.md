# 视觉识别模块：标签字母 + 视觉模型

> RE:BENCH（JUNCTION CHINA 2026 具身智能赛道）· 负责：视觉识别
>
> 本文说明**现有实现的真实状态**：哪些验证过、哪些还没验证、卡在哪。不把"没跑过的东西"写成"已完成"。

## 1. 一句话结论

积木的身份不靠颜色，靠贴在积木上的**白底黑字标签**：找到矩形标签 → 读出上面的字母 → 这就是一件物体。字母有两条独立的读法——本地模板比对（离线、需现场登记）和视觉大模型（免登记、需联网），默认两条一起用，谁有把握听谁的。**没 key、没网时系统照常工作**，只是退回模板比对。

## 2. 现在怎么跑

```bash
# 1) 实时视觉（手机当相机，HTTPS 必需：http 下浏览器禁止取摄像头）
python -m vision.tools.phone_live --port 8300
#   手机打开 https://<电脑IP>:8300 → 高级 → 继续前往

# 2) 桌面摄像头（本机 USB/内置相机）
python -m vision.main --camera 0 --config vision/config/desktop.json --mode real

# 3) 全量离线回归（不需要摄像头）
python -m unittest vision.tests.test_vision -v
```

想启用视觉模型，多一步自检：

```bash
set DASHSCOPE_API_KEY=sk-xxxx           # PowerShell: $env:DASHSCOPE_API_KEY="sk-xxxx"
python -m vision.tools.vlm_check        # 报配置是否生效 + 现场画 A/B/D 测认字
python -m vision.tools.vlm_check --image working/_scratch/real_ab.jpg   # 用真照片，模板读数并排对比
```

自检通过后重启 `phone_live`，手机页面底部标签行会从 `[模板比对（模型未就绪：没配 api_key）]` 变成 `[模型+模板 qwen-vl-max]`。

## 3. 数据流

```
手机/相机帧 (1280×720)
   │
   ├─ find_labels()         Canny + 轮廓 + 四边形拟合 + 长宽比过滤 → 每张标签 4 个角点
   │
   ├─ normalize()           透视拉正到统一尺寸的 tile
   │
   ├─ character_mask()      Otsu 二值化（有兜底）→ 48×48 字形
   │        │
   │        ├─ LetterBank.recognize()   24 档角度 × 2 尺度 × 矩阵乘 Jaccard → (字母, 分数)
   │        │
   │        └─ VlmReader.peek()/warm()  缓存命中→字母；未命中→丢后台线程，本帧先用模板
   │
   ├─ _fuse()               两者合流 → (字母, 分数, 来源)
   │
   └─ Detection(object_id="block_A", letter="A", letter_score=0.87, bbox, ...)
            │
            └─ zones.assign() → StabilityTracker(5 帧) → 快照 JSON → diff
```

**读不出字的标签不产出物体。** 这条是硬的：以前会给它造一个 `unknown_00N`，结果一张真实照片冒出 3–13 个幽灵物体（白纸上一条无关横线凑到 0.59 分就算"物体"），把缺件判断和 issues 数全带歪。现在只留一条 `label_unread:<bbox>` 说明"这儿有张标签我没读出来"。

## 4. 字母识别（模板比对）

### 4.1 为什么不用颜色定身份

现场桌面是紫红的，S 中位 133——比大多数物体还"高饱和"；紫光灯把绿积木染成 H=123（配置里绿色是 40–85），红积木又被自己的白标签切成两半。颜色定位给出的 bbox 一个是画面外的东西、一个只有半截。而白底黑字的标签在 HSV 上离桌面很远。所以 `label.primary = true`：**标签就是定位依据，颜色完全不参与**。

颜色那条路还在（`primary=false` 时用），只是不再当主力。

### 4.2 任意角度

积木靠手摆，字跟着积木转。只试 0/90/180/270 时，歪 20° 四个正交朝向全对不齐，自比分数 0.45–0.61，全部掉到阈值以下。

现在绕笔画质心连续转 24 档（15° 一档）。两个必做细节：

| 细节 | 不做会怎样 |
|---|---|
| 先扩画布到对角线尺寸再转 | 48×48 直接转 45°，A 的尖顶被裁掉 |
| 转完按笔画外接框重新贴回 | 45° 后外接框从 48×24 变 53×53，字形自动"变小" |
| 先转后缩，顺序不能倒 | `_rotate` 会重贴归一化尺寸，先缩会被抹平 |

加速：把每个形态的平移版本摊成矩阵行，一次 sgemm 算完所有 Jaccard（`inter = q@mat`，`union = |q|+|t|-inter`）。24 档从 31.7ms 降到 **4.3ms**。

实测：同字母转任意角度重采样后自比最低 **0.817**；A 的字拿去认 B，24 个角度里最高只有 **0.51**。阈值 0.6 卡在两者之间（原定 0.55 太低，会把别的字母认成本字母）。

### 4.3 二值化踩过的坑（都已修）

| 现象 | 根因 | 处理 |
|---|---|---|
| A 的笔画碎成噪点，ink 607→274 | 采样宽度 96 太窄，原图笔画 3–4px 缩完只剩 1.5px | `CANON = 192` |
| 整张图被判成"全是墨"（ink 0.83–0.90），候选被闸门拒掉 | Otsu 是全局阈值，画面多一圈亮边就被带偏 | `_trim_border` 挪到**二值化之前**，按 CANON 固定裁 8px（按短边取比例正好落在 5px 悬崖：4px 时 ink 0.11、6px 起稳定 0.34） |
| B 的分数在 0.53 / 0.93 之间横跳 | 打分公式 `min(ink,0.35)-|ar-1|*0.05` 实际在**奖励笔画多**的候选，而过度分割永远笔画更多 | 改成 **Otsu 优先，自适应只在 Otsu 抓漏（ink<0.12 且多 1.5 倍）时补位** |
| 标签找到了却提不出一个笔画像素 | `_order_quad` 用"最小 sum / 最小 diff"排序，矩形转到 40° 时最上角同时是最左角，argmin 两次返回同一点 → 透视变换退化 | 改按**质心极角**排序（这个 bug 本身是真的，虽然当时是从旧测试脚本的深色填充里发现的） |
| 679×387 的纸横线被当标签 | 拉正后是 96×8 一根线 | `find_labels` 加长宽比过滤 0.25–4.0 |

### 4.4 压力测试（B，22 种扰动）

缩放 70–145% / JPEG 35–95 / 亮度 ±25% / 模糊 / 噪声 / 旋转 ±12°：

- 16 种稳定在 0.91–1.00；`jpeg65` 0.70→0.911，`noise` 0.705→0.994
- p25 = 0.911，中位 **0.924**
- 剩余 5 个旋转 case 卡在 0.50，根因见 §8

## 5. 视觉模型（VLM）

### 5.1 为什么要它

模板比对要求**现场把每个字母登记一遍**，而且对手写差异敏感（手写 D 和 B 很容易混）。用户报的"加了 D 还是认不出"，一半是登记时存错了字（见 §7.2），另一半是字形本身太像。模型不用登记、能认任意字母、对歪斜和光照更宽容——**新摆一块没登记过的积木，它直接读出来**。

### 5.2 为什么不装第三方库

这台机器 `requests` / `openai` / `torch` / `pytesseract` 全都没有（ModuleNotFoundError），`api.openai.com` 也不通。所以 `vision/vlm.py` **只用标准库 `urllib` + `json`**，走 OpenAI 兼容的 `/chat/completions`。换 `base_url` 就能用通义 / 豆包 / 智谱 / Kimi / 本地 vLLM / Ollama。

### 5.3 三种读法

| `label.reader` | 行为 | 适用 |
|---|---|---|
| `template` | 只用模板库 | 断网、纯离线，与引入模型之前一字不差 |
| `vlm` | 只用模型，**不偷偷混模板结果** | 不打算登记，模板库可以空着 |
| `auto`（默认） | 模型为主、模板校验；没 key 自动退回 template | 现场主用 |

### 5.4 合流规则（`Detector._fuse`）

分数是"这个字母有多可信"，不是模型概率（模型不返回概率，0.95 只是"模型认出来了"的记账值）。它和模板分数共用阈值 0.60，所以必须同量纲：刚过线 0.60、很确定 0.95–1.00。

| 模型 | 模板 | 结果 | 来源标记 | 理由 |
|---|---|---|---|---|
| 有答 | 没有 | 用模型，0.95 | `vlm` | 这就是认不出 D 的解法 |
| 有答 | 同一个字母 | 用模型，`max(模板, 0.95)` | `both` | 两条独立的路互证，没理由压分 |
| 有答 | 不同，模板 < 0.8 | 用模型，0.95 | `vlm` | 0.6x 只是闸门，算不上"另一派意见" |
| 有答 | 不同，模板 ≥ 0.8 | 用模型，`th+0.02` | `vlm_conflict` | 真打架：听模型的但压到刚过线，页面标 ⚠️，现场看得出有争议 |
| 没答/还在算 | 有答 | 用模板 | `template` | auto 的兜底价值 |
| 没答/还在算 | 没有 | 空 | `vlm_wait` / `vlm_blank` | 不产出物体，只留 issue |

### 5.5 不阻塞实时流

一次调用 0.5–3 秒，手机页每秒要好几帧。所以：

- `peek(tile)` 只查缓存，立刻返回（没结果就 None，本帧先用模板顶着）
- `warm(tile)` 丢后台队列，2 个 worker 并行，算完写缓存
- 缓存 key 是 **16×16 aHash**（灰度与自身均值比）
- **同一张图"正在算"时不重复入队**（`_inflight` 集合去重）

后两条都是踩出来的，不是优化：

| 原始写法 | 后果 |
|---|---|
| key = 32×32 灰度的 blake2b | 手机每帧 ±2 传感器噪声就让 key 变一次 → 每帧都排队、每帧都调模型，缓存等于不存在 |
| 单 worker、无去重 | 三块积木排在一条 1.2s 的队上，最后一块 2.4s 才轮到；且 6 帧就能把 16 格队列塞满 → 实测"只认得出第一块" |
| 失败了每帧重排 | 端点挂了就拿队列当 DoS 工具打自己 |

现在**连续失败 3 次就自行停用**（`given_up`），`available` 转 False，页面显示"模板比对（模型未就绪：连续失败已停用（HTTP 401…））"。不投降的话页面一直显示"模型+模板"、实际一次没通——这种"假装在工作"最难查。

## 6. 配置说明

`vision/config/desktop.json` → `label` 段：

```json
{
  "enabled": true,
  "primary": true,
  "bank": "vision/config/letters.npz",
  "match_threshold": 0.6,
  "angle_step": 15,
  "reader": "auto",
  "vlm": {
    "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
    "model": "qwen-vl-max",
    "api_key": "env:DASHSCOPE_API_KEY",
    "timeout_s": 8,
    "max_side": 512
  },
  "canny": [60, 160],
  "min_area_px": 3000,
  "max_area_ratio": 0.10,
  "min_side_px": 40
}
```

| 键 | 含义 | 调它会影响什么 |
|---|---|---|
| `match_threshold` | 模板分数闸门 | 调低→认错增多；调高→认不出增多。0.6 卡在自比 0.82 / 交叉 0.51 之间 |
| `angle_step` | 角度搜索步长（度） | 30° 时最坏角误差 15°，自比从 0.82 掉到 0.59；15° 是实测下限 |
| `min_area_px` / `max_area_ratio` | 标签面积范围（px² / 画面占比） | 手机拿远了标签变小会被漏掉 |
| `canny` | 找框的边缘阈值 | 桌面反光时容易把标签和旁边连成一体 |
| `api_key` | `env:变量名` 从环境变量读 | **别把 key 提交进仓库** |

`letters.npz` 是登记库，`letters.json` 是它的人类可读摘要（每个字母几个模板）。

## 7. 现场操作手册

### 7.1 登记 / 删除

```
画面里只放一块积木 → 输入它的字母 → 点「登记字母」
登错了 → 输入字母 → 点「删除」
```

- **画面里有超过一张标签时拒绝登记**，并列出每张像什么。这不是谨慎，是必须：以前取"面积最大的标签"，桌上 A、B 都在时登记 D，存进去的是 A 的笔画，而 enroll 是追加——**错误模板永久污染库**，之后那块真 D 永远认不出、还会被认成 A。
- 登记前用**旧库**自检一遍，若这张字在旧库里已经是某个字母（≥阈值），提示 `⚠️ 这张字更像 A（0.93）`。入库之后自比必然是 1.00，那时就什么都看不出来了。
- 常见症状对照：

| 症状 | 真因 | 处理 |
|---|---|---|
| "加了 D 但 D 不认" | 登记时存错了字（存成了 A） | 删除 D → 单独放 D → 重新登记 |
| "B 一会 0.9 一会 0.5" | Otsu 被贴纸外亮背景带偏 + 打分公式奖励笔画多的候选 | 已修（见 §4.3），若仍抖，看是不是标签贴歪导致框变大 |
| "标签被找到但一直读不出" | 字太细/太白、反光、标签离镜头太远 | 逼真一点：笔画粗、黑笔、白纸，标签占画面 ≥ 1/10 |
| "凭空多出一个物体" | 以前会把读不出的标签造成 `unknown_00N` | 已修：读不出就不产出物体 |

### 7.2 建议的现场顺序

1. 先把所有积木（含新的 D）**一块一块单独登记**，画面里只留一块
2. 全部登记完，再把它们一起摆好
3. 点「建立基准」→ 挪动一块 → 手退出画面 → 「与基准比较」
4. 页面底部标签行确认读法：`[模板比对]` 或 `[模型+模板 qwen-vl-max]`，以及每张标签读到什么、多少分、最像的朝向

```
  OK  转     0°  身份 ['block_A', 'block_B']   A 0.87@0° | B 0.91@0°
  OK  转    20°  身份 ['block_A', 'block_B']   A 0.92@0° | B 0.92@0°
  OK  转    40°  身份 ['block_A', 'block_B']   A 0.84@0° | B 0.96@0°
  OK  转    70°  身份 ['block_A', 'block_B']   A 0.85@180° | B 0.87@180°
  OK  转   200°  身份 ['block_A', 'block_B']   A 0.85@180° | B 0.86@180°
```

> ⚠️ **一次自我更正**：早先这里记的是"20° 漏掉 A，Canny 把标签和相邻的边连成一体
> （框 99×192）。修复要先做标签内部连通域分割"。后来复核发现**那是测量工具造的缺陷**：
> 旋转测试用了深色画布填充，在画面里造出一条笔直的斜暗边，A 的标签正好压在边上，
> 于是 Canny 把标签和这条**本来不存在的边**连成一体 —— 框从 270×134 涨到 849×514、
> 还贴着 y=0，墨量 587→911，分数掉到 0.47。换成 `BORDER_REPLICATE` 填充后，
> 20° 是 A 0.92 / B 0.92。
> 结论：**测量工具本身会造缺陷。看到可疑结果先怀疑自己的构造方式**，别急着改生产代码。

### 未验证 / 已知问题

1. **视觉模型没跑过真实 key**。代码路径、协议形状、异步时序都用假服务验过，但"qwen-vl-max 到底认不认这手写体"没验过。拿到 key 第一件事跑 `vlm_check`，别等答辩。
2. **标签变小后找框会漏（已定位到具体代码行）**。手机退到 2.5 倍距离（整幅缩到 40%）时，B 的标签轮廓被 `approxPolyDP` 近似成 **8–9 个顶点**，撞上 `find_labels` 的 `len(approx) != 4` 硬门槛，整张标签进不了候选；认字那一步根本没轮到。45% 时还是干净的四边形、两块都认对。修复方向：顶点数 4–6 时取凸包，或 `minAreaRect`（永远 4 个角）兜底，仍用长宽比 + 内部亮度把关。**但没改**：这道门槛同时挡着桌面纸横线拼出的假标签（679×387，拉正是 96×8 一根线），放宽必须连带重跑 79 项测试 + 7 张夹具 + 22 种扰动压力表。`find_labels(..., stats=[...])` 现在会把每个候选的拒绝原因吐出来，查这类问题不用再抄一遍 Canny 流程。
3. **剩 5 个旋转 case 卡 0.50**。tile 里混进贴纸外背景时，`_trim_border` 只裁边、裁不掉四角的背景三角形，笔画里混进了标签自身的边框。试过"中位与最暗 3% 的中点"当阈值，没救（A 的旋转变成了 None），所以保留现状。
4. **视觉模型没配 key 时，"不止两个方块"要靠现场登记**。纯模型模式（`reader=vlm`）在库里没有任何字母时也能工作，`expected_ids()` 会返回空表（不拿颜色 ID 去报假缺件），但"应该有哪几块"就无从检查了。
5. **找框会误抓桌面纸片**。标签出画时会从桌面横线纸上凑出矩形，被读成 A 0.51 / B 0.54 —— 靠分数闸门兜住，不会产出物体，但 `label_unread` 里会出现这些假框的坐标，看图时别被误导。
6. **像素坐标不是抓取坐标**。`center_px` 只是图像平面上的位置，转机械臂空间需要相机内外参 + 手眼/基座标定 + 安全验证，属队长对接，本模块不提供。
7. **没接过 GALBOT G1**。所有验证都在桌面 USB/手机摄像头上，`CameraAdapter` 换源即可，但换相机必须重标分辨率 / HSV / 区域。

## 11. 交接要点（给 B / C / 队长）

- **给 B**：`/frame` 每帧返回 `objects`、`issues`、`quality_ok`、`labels`（每张标签的字母/分数/朝向/来源）、`reader`（当前读法）、`vlm`（调用统计）。标签行可直接展示，不必自己解析。
- **给 C**：`object_id` 是 `block_<字母>`；读不出字的标签**不产生物体**，所以"少了一块"可能是"读不出"而不是"被拿走"——看 `issues` 里的 `label_unread`。
- **给队长**：`reader=auto` + 无 key 时行为与之前完全一致（纯模板比对），所以接模型这件事**不会让现有链路变得更脆**。
- **红线**：`label_pending` 是"模型还在读"的过渡态，不是画面缺陷，不计入 `quality_ok`；任何 `label_unread` / `label_empty` 都应停留在待复核，不得判成"物体被拿走"。
