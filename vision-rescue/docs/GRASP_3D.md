# 三维目标定位与抓取接入（2026-11-07）

## 一句话结论

**框选 → base_link 三维坐标 → 逆解可达性** 这条链已在真机上跑通，全部只读、不发运动。
真正的拦路虎不是算法，而是**左手臂深度相机当前近乎水平地掠视桌面**（光轴仅下倾约 5°），
对桌面的几何严重退化——这也是"东西要很近才能识别"的物理根因。

## 已验证的事实

| 项 | 来源 | 结果 |
|---|---|---|

## 发现的三个坑

1. **`get_sensor_extrinsic` 与 `get_transform` 不是同一套坐标约定。**
   头部相机 `get_sensor_extrinsic` 给出 (0.271, 0.028, 1.324)，`get_transform` 给出
   (0.034, 1.334, 0.214)——分量被重排过。以 FK 结果为基准校验：FK 与 `get_sensor_extrinsic` 完全一致，
   所以统一走 FK。

2. **头部相机是鱼眼（`shitong-fisheye`），但 `D` 全为 0，只能当针孔用。**
   把手臂点云按针孔投影叠到头部画面上，错位会非常明显（散在人脸和背景上）。
   **因此跨相机投影暂不可信，三维一律在深度相机自己的像素坐标系里算。**

3. **`get_gripper_tcp_link` / `left_gripper_*` 帧时有时无。**
   同一份代码两次运行，一次 FK 成功一次 `INVALID_INPUT`，`get_supported_links()` 里的夹爪帧
   也会整批消失。怀疑与末端工具注册状态有关。**已改为优先 TCP、取不到自动退回腕部安装帧。**

## 实现的接口

机器人侧常驻代理 `robot_agent.py`：一次 `init`，按 JSONL 走 stdin/stdout。
经 SSH 以 **base64 单 token** 注入 `python3 -c`，**机器人上不落盘**。

```
{"cmd":"view"}                     → 6 帧中位深度视图(JPEG) + 实时相机位姿 + 末端位姿
{"cmd":"target","roi":[x,y,w,h]}   → 选区内三维中位点 + 离散度 + 到末端距离 + IK 结果
```

- `GET /depth` → 深度视图 JPEG + 元数据
- `POST /target3d {"roi":[...]}` → 三维坐标 + IK

- 抓取姿态只沿用当前末端朝向，**没有做抓取朝向规划、没有碰撞检查实践、没有夹爪开口计算**。

## 突破（2026-11-07 11:50）：绕过规划器，直接关节通路成功

### 1. 规划器为什么全 FAULT —— 不是姿态问题
`service_motion_plan` 每次规划都返回 `FAULT`，连"规划到当前姿态"也是。
日志根因：`Failed to read whole body state from WBC` / `MpsTask start state: failed to obtain start robot state`，
重试 10 次全失败。**该故障早于本次调试**（09:04 起就有），重启机器人也没恢复。
所以 `motion_plan` / `check_collision` / `set_end_effector_pose` 这条"规划 + 碰撞检查"的路**当前不可用**。

### 2. 可用通路：`set_joint_positions`
```python
GalbotRobot.set_joint_positions(angles7, joint_groups=["left_arm"],
                                is_blocking=True, speed_rad_s=0.12, timeout_s=40)
# -> ControlStatus.SUCCESS
```
- 零位移自检：下发当前角 → `SUCCESS`，角度不变，证明通路可用。
- 实测关节跟踪误差 **< 0.1°**（闭环精度很高）。
- **代价：没有碰撞检查。** 必须自己用小步插值 + 目视看护。

### 3. ⚠️ 安全：不要调用 `request_shutdown()`
`robot.request_shutdown()` 会触发**整机正常关机**（`last -x` 可见 `shutdown system down`），
不是只退出 SDK 实例。收尾只调 `r.destroy()`。

### 4. 姿态怎么定：不要"往下转"，要"往上折叠"
原姿态腕部在桌面高度附近平视（相机 pitch **上仰 16.7°**），直接往下转会把夹爪压进桌面。
而且保持原姿态做纯平移抬升（lift）→ IK 全部 `FAULT`，不可行。
可行解是**同时抬升 + 转腕**（单一 IK 目标）：

- 目标：相机朝前下方 55°，位置 (0.34, 0.20, 1.12)
- 关节增量最大 ≈ 99°（j2 肩部上抬约 99°，j7 腕滚 ~85°）
- 关节空间线性插值的 FK 预演显示：**腕部高度全程不下降**（最低点=起点 0.858），是"往上折叠"不是"往下扫"

分 4 段执行（25% → 50% → 75%），每段速度 0.12 rad/s，每段后核验关节与相机 pitch：

| 段 | 相机 pitch（下俯） | 相机高度 |
|---|---|---|
| 起始 | −16.7°（上仰） | 0.912 |
| 25% | −4.9° | 0.953 |
| 50% | 38.1° | 1.035 |
| 75% | **59.1°** | **1.100** |

停在 75%（59.1°）——已经够用，没有再走最后一段。

## 补充（13:20）：一次性抓取为什么替代了"逐格试探"

之前一格一格往下探，**不是深度相机没用**，而是标定错了两处，导致"什么时候该停"定不下来：

1. 指长按 17.6 cm 算，实际 **18.9 cm** → 每次都少降 1.3 cm
2. 腕部相机偏工具轴 7 cm → 画面中心不等于夹爪正下方

两处修正后，落点可以直接由深度算：

```
mount_z = 物体顶面 top_z + 指长(0.189) − 抓深(0.025)
```

流程变成：**一次扫描 → 高空对准 → 单次垂直下降 → 合爪**，不再分步试。

配套实现：`robot_exec.py` 的 `find` / `ik` 命令 + `tools/oneshot_grasp.py`。
实测：扫描 627–989 ms，对准 339 ms，单次下降 122–2000 ms（取决于距离与速度），合爪 393 ms。
