## 2. 真正成功的做法：先绑定身份与几何，再连续执行

**成功不是“找深度最高点就抓”，也不是每一步问模型。**

1. 用外部视觉获取目标身份、二维框。用实测相机参数与腕部深度核对三维位置、桌面和目标高度；有多个峰/遮挡时不能拿一个中位点直接下抓。
2. 已验证的对象先做一份完整动作计划：高位对准 → 张爪 → 垂直接近 → 合爪 → 宽度检查 → 短抬升 → 检查持物 → 高位运输 → 盒口上方释放 → 上提。
3. 一段 batch 直接执行，步骤之间按反馈衔接；不在动作之间插入聊天模型。第一次采用新抓法可在短抬升处设检查点，确认后再继续运输。
4. 合爪后的宽度大于空爪值只能表示可能夹住东西；还要结合抬升前后图像确认目标随夹爪移动。不能仅凭 effort 或“命令 SUCCESS”宣称抓到。
5. 下探失败、夹空、碰撞服务失败、反馈陈旧、定位不明确时停止；不要重复闭合、继续下探或拿旧坐标盲试。失败后抬回也是一个新的、经过检查的运动步骤。

## 3. 坐标和几何：最容易浪费几小时的坑

- 所有运动 xyz 单位米，基座坐标系 `base_link`，是**工具安装帧** `left_arm_end_effector_mount_link` 的位置，不是指尖/物体中心。
- 本轮工具轴为 mount 的 +X，朝下时近似 world -Z。历史工具长度 .189m，所以朝下时 `tip_z≈mount_z-.189`。这是交接估计，尚未严谨重新标定；不能把它当万能精度保证。
- SDK 头部图像虽然物理镜头是 fisheye，输出却是**已校正 plumb_bob、D全零**。按实时内参做针孔反投影；再次套等距鱼眼公式会产生约6cm偏差。这是绿色成功前的关键修正。
- 当前实际图像1280×960。视觉模型有时声称1024×768，却返回归一化框；必须按**实际图片尺寸**换算。裁剪/放大后要保存裁剪偏移和缩放，不能直接用裁剪像素当全图像素。
- 外部模型在全图里反复把鼠标误认为白色玩具、把远处手或机器人误认为目标旁的手。局部裁剪放大再识别有效；先核对空间位置，不能全图一报“hand”就反复让用户确认，也不能无依据忽略真实手。
- `scene_regions` 将腕部深度投影到头部二维框，按高度过滤。输出 `center/top_z/xy_p10/xy_p90/n`；**ok只表示点数≥60，不保证这些点属于目标。** 低物/透明瓶/金属/遮挡下可能只采到桌面或邻物。
- `probe` 用来读桌面、凸起，不负责身份。最高凸起可能是瓶子、电脑、盒沿。需要把视觉框和点云匹配，不能用“最近峰/最高峰”替代物体识别。
- 相机随关节姿态变化；动作后使用实时外参。桌面本轮约 .710–.715m，必须按目标附近测量，不能选择更低的旧数值只为了通过检查。
- SDK 碰撞检查只覆盖已知模型，现实桌面杂物不一定建模；不要声称 collision SUCCESS 就代表桌面没有障碍。

## 4. API 已踩过的坑：照现有实现走

- `check_collision_detail([])` 曾 FAULT，日志 `Failed to read whole body state from WBC`。不是许可绕过碰撞检查。
- 现有执行器给每个采样构建 `RobotStates.whole_body_joint`，顺序 leg/head/left_arm/right_arm，再调用碰撞服务；真机 SUCCESS。官方依据见 `https://developer.galbot.com/docs/SDK/1.10.0/g1/zh/examples_python` 详细碰撞检测章节。没有证明 WBC 空状态读取问题本身被修复。
- IK 返回值带角度但状态非 SUCCESS 仍拒绝。`move_checked` 一次 RPC 内完成新预演、几何检查、完整状态碰撞检查与同一关节解执行；不得重新求一个解后跳过原预演。
- 计划一次性、15秒过期；关节漂移>.5度拒绝；名义tip离桌至少12mm，max_delta≤45度，max_dev≤8cm，速度≤.12rad/s。不要为通过报错随意放宽。
- 早期某次高位运动执行反馈误差3.14mm，触发3mm阈值停止；随后只读复查已到目标。说明有到位反馈时序问题，应研究新鲜反馈与稳定判据，**不是把误差阈值改大就算修好**。低位动作不应盲目重试。
- `plan.collision_checked=false` 是IK预演阶段的标记；执行阶段另有实际完整状态碰撞检查，不要只看嵌套plan误判绕过了检查。后续可改日志明确标注执行检查结果。
- 夹爪默认根据新鲜timestamp和连续稳定反馈完成；无需再固定sleep数秒。effort过去常为9.54，最后一次球尝试也出现23–30，均不能单独作为持物/触桌判断。
- 通信超时后运动结果未知，不能自动重发；先读取实际状态。

## 5. 已实现的提速与真正剩下的工作

- batch实测软件步骤间 gap约 .08–.19ms；主要延迟是机械运动、重复初始化、图像传输和聊天模型决策，不要再加每步sleep。
- fast：高位运输 .12rad/s，接近 .06，夹爪 .07m/s；精细抓取可显式speed=.04、v=.035。运输速度已在真机使用；不同路径不能据此算固定提速百分比。
- 一物体使用一次视觉定位、确定性动作串和结果检查；异常才额外识图。跨对象保持连接可省SDK初始化，但退出必须释放资源，不能遗留多个控制客户端。
- 用户最新希望：**除了识图，其余全部脱离AI**。现有只是执行底座，完整自主状态机还没完成，不能谎称已经有。
- 建议在本机新增状态机：`OBSERVE→LOCALIZE→PLAN→APPROACH→GRIP→VERIFY→TRANSFER→PLACE→DONE`，每个状态由实际反馈转换；失败进入明确错误状态，不用聊天模型选下一步。先支持已验证的积木抓法，再独立验证玩具、瓶子、卡尺的抓法。
- 外部视觉返回结果须校验schema、框范围、置信度和目标身份；三维定位不合格就拒绝。瓶子须直立放置，不像积木从盒口上方直接丢；卡尺右桌沿先做可达性检查。
